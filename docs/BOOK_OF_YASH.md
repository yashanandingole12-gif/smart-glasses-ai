# SECTION L — IIoT REFERENCE (compact)

- **Edge vs cloud:** edge for low latency, privacy, offline; cloud for fleet analytics/training.
- **Digital twin:** live model of an asset synchronized with real data for simulation/monitoring.
- **Predictive maintenance:** vibration (FFT, RMS, kurtosis), temperature, current signature → anomaly detection → remaining-useful-life. Condition-based > time-based maintenance.
- **KPIs:** OEE = Availability × Performance × Quality.
- **Security:** IEC 62443 (segmentation, zones/conduits), don't expose PLCs to the internet, VPN/TLS, patching, least privilege.

# SECTION P — EVA HARDWARE ARCHITECTURE

**Principle:** the glasses are a **thin, stateless, low-power sensor/IO node**. They hold **no personal memory**. The phone is the brain. A stolen pair of glasses should reveal nothing.

```text
GLASSES (XIAO ESP32-S3)                        PHONE (Android)
 ├─ INMP441 I2S mic ──────────┐
 ├─ Camera (on demand) ───────┤  BLE (control, events, wake)
 ├─ MAX98357A + speaker ◄─────┼─ Wi-Fi (audio/camera bulk, on demand)
 ├─ IMU (head motion / voice vibration)
 ├─ Touch/button (physical confirm)
 ├─ OLED (optional status)
 ├─ On-head/proximity sensor
 ├─ LiPo + protection + charger
 └─ LED (camera-active indicator)
```

| Block | Choice | Notes |
|---|---|---|
| MCU | **XIAO ESP32-S3** (dual-core LX7, Wi-Fi + BLE 5, vector instr., PSRAM on Sense) | ESP32-C3 = lower-power alternative but weaker for audio/vision |
| Mic | INMP441 (I2S, 24-bit) | Uses I2S RX; keep clock lines short |
| Audio out | MAX98357A I2S class-D + small speaker | Uses a *separate* I2S TX bus/pins; watch battery current spikes (decoupling caps) |
| Camera | OV2640 (Sense) | Duty-cycled; JPEG frames; LED on when active |
| Display | Small OLED I2C | Optional; status only |
| Power | 1S LiPo + protection + fuel gauge | Temple-arm weight/heat limits; target sleep <1 mA |
| Physical confirm | Capacitive touch or button | Needed for Level 3/4 actions (Section T) |

**Practical warnings (verify against the actual board pinout):** XIAO ESP32-S3 exposes few free GPIOs; camera, two I2S buses, I2C OLED, button and IMU can conflict. Budget pins first; a second small MCU or I2C GPIO expander may be needed.
**Audio math:** 16 kHz · 16-bit · mono PCM = 256 kbps → BLE alone is too thin; use Wi-Fi for streaming or on-glasses Opus (~16–24 kbps) over BLE.
**Power strategy:** deep-sleep default → wake on button/IMU tap/VAD → BLE advertise/connect → Wi-Fi only when bulk data is needed → sleep. Camera never streams continuously.

# SECTION S — VOICE ACTIVATION & AUTHENTICATION

**Core axiom: `WAKE WORD ≠ IDENTITY ≠ AUTHORIZATION.`** Saying "Hey EVA" wakes the system; it proves nothing.

```text
Mic → VAD → Wake word → Wearer-presence check → Speaker verification (+anti-spoof)
   → Device authentication → Context check → Command classification → Risk level
   → Authorization (step-up if needed) → Execute → Audit
```

| Stage | Method | Purpose |
|---|---|---|
| VAD | WebRTC VAD / Silero | Only listen while speech present |
| Wake word | Small keyword model, tuned threshold | Low false-accept; not identity |
| **Wearer presence** | On-head sensor + **IMU voice-vibration correlation** (speech from the wearer's skull/jaw matches the audio) | Rejects TV, other people, most replays |
| Speaker verification | On-device embedding (ECAPA-TDNN/x-vector class, TFLite) vs enrolled voiceprint, cosine threshold; multi-session enrollment across noise levels | Probabilistic identity, *not proof* |
| Anti-spoof | Replay/synthetic-speech detector (ASVspoof-style) + randomized challenge phrase for elevated actions | Recorded/deepfake voice |
| Device auth | Bonded BLE glasses + app-layer signed/encrypted session | Unauthorized glasses/phones |
| Phone state | Unlocked / trusted place / recent biometric | Stolen-phone defense |
| Risk engine | Deterministic rules (Section T) | Decides what's allowed |

**Auth states:** `LOCKED → VOICE_TRUSTED (S0–S1 only) → STEP_UP (challenge/tap) → PHONE_UNLOCKED (biometric, S2–S3) → CRITICAL (physical confirm + biometric).` Timeouts shrink as sensitivity rises. State drops to LOCKED on glasses removal, phone lock, BLE loss, or repeated failed verification.

**Limits to be honest about:** voice verification has non-zero false-accept/false-reject rates and modern voice cloning can defeat naive systems. That is why **voice alone never authorizes S2+ actions.**
**TV/radio:** wearer-presence + IMU correlation + "audio came from the glasses mic near-field" heuristics; ignore wake words in playback (acoustic echo cancellation against known playback).
**Accidental activation:** wake-word threshold + short activation window + a confirmation earcon; no action on ambiguous audio.

# SECTION T — SECURITY ARCHITECTURE

### T1. Sensitivity × authorization

| Level | Examples | Requirement | Output rule |
|---|---|---|---|
| **S0** Public | Time, weather, technical facts, music | Wake + wearer-present | Speak freely |
| **S1** Personal | Preferences, project status, non-sensitive schedule | + speaker verification | Speak if no strangers detected |
| **S2** Private | Contacts, messages, location history, physiology, personal notes | + phone unlocked or step-up | Prefer private audio path/phone screen; ask before speaking |
| **S3** Highly private | Emotional/relationship history, habits, health, sensitive memories | + biometric **and** private context | **Never auto-spoken when others may be near**; show on phone or speak only via private audio |
| **S4** Critical | Send money/messages to new contacts, delete memory, change auth, factory reset, export data, unlock things | + biometric + **physical confirm on glasses** + optional cool-down | Confirm out-of-band, never by voice alone |

### T2. Threat model

| Threat | Defense |
|---|---|
| Another person says "Hey EVA" | Speaker verification + wearer-presence + risk gating |
| Recorded voice / replay | Anti-spoof, IMU correlation, challenge phrase, nonce |
| Deepfake voice | Voice never sufficient for S2+; phone biometric / physical tap |
| TV/radio commands | AEC, wearer-presence, near-field check |
| Accidental activation | Thresholds, earcon, no risky action without confirmation |
| Stolen phone | Keystore keys require user auth; auto-lock; remote wipe; key expiry without check-in |
| Stolen glasses | No personal data on glasses; bond revocation; on-head + bond required |
| Rogue Bluetooth device | LE Secure Connections + bonding + app-layer authenticated encryption (X25519 → HKDF → ChaCha20-Poly1305) with counters/nonces (anti-replay) |
| Malicious apps | Least-privilege permissions, private app storage, no exported components, Play Integrity/root detection |
| SMS/notification snooping | Access only after S2 auth; redact on lock screen |
| Memory theft | SQLCipher + Keystore-wrapped keys; S3+ in a separate DB requiring biometric unlock |
| Prompt injection via camera/OCR/SMS/web | Treat all external text as untrusted data; tools can't be triggered by content; Policy Engine outside the LLM |
| Bystanders overhearing | Sensitivity-aware output routing; "others nearby" check (mic diarization, BLE/device count, user setting) |
| Shoulder-surfing screens | Auto-hide S2+ content |
| Data exfiltration by online tools | Per-tool network allowlist; S2+ never sent to cloud unless he explicitly opts in |

### T3. Data protection
- **At rest:** SQLCipher (AES-256). DB key wrapped by an **Android Keystore** key (StrongBox/TEE where available) with `setUserAuthenticationRequired`. Separate keys per sensitivity tier (S0–S2 one key, S3 another, S4 secrets in Keystore only).
- **In transit:** authenticated encryption on the BLE/Wi-Fi link (not just link-layer); TLS 1.3 for any online call; pin certificates for own hub.
- **Deletion:** `secure_delete` + VACUUM; **crypto-erase** by destroying the tier key; "forget this" also removes embeddings and derived summaries.
- **Audit log:** append-only, hash-chained (each entry includes hash of previous), records: time, actor state, command class, decision, tier accessed. Never logs private content itself.
- **Lost-device mode:** revoke bond; wipe keys; require re-enrollment; optional remote lock via a second trusted device.
- **Backups:** end-to-end encrypted with a user-held key; opt-in only.

### T4. Voice privacy (Part 24)
`Low-power wake detection → short activation window → STT → process → discard audio.` Ring buffer ≤ a few seconds, held in RAM only. **No raw audio persists unless he explicitly authorizes it** (per-session, visibly indicated). Voiceprint is stored as an embedding in the S3 tier, not as recordings. Camera activity is always indicated by LED.

# SECTION U — PHYSIOLOGICAL CONTEXT SYSTEM

**Signals:** heart rate/HRV, skin/body temperature, motion/activity (IMU), voice features (pitch, energy, rate), environment (noise, light, place).
**Golden rule:** these are **contextual signals, not emotion detectors.** EVA forms *hypotheses* with confidence and never announces "you are sad/anxious/in love."

```text
raw signal → clean (motion filter) → per-user baseline (time-of-day, activity) → z-score / deviation
          → fuse with context (stationary? conversation topic? voice change?) → arousal hypothesis + confidence
          → policy: adapt behavior, or ask; never assert
```

| Observation | Allowed inference | Not allowed |
|---|---|---|
| HR high + stationary + quiet voice + personal topic | "Possible elevated arousal" (conf ≈ 0.3–0.5) | "You are anxious/sad/in love" |
| HR high + recent movement/stairs/caffeine | "Explained by activity" | Any emotional inference |
| Persistently low activity + late nights (weeks) | Suggest a routine check-in | Diagnosis |

**Allowed uses:** soften tone or shorten replies; avoid pushing notifications; gently ask ("Want to slow down?"); log trends for *him* to review; suggest breaks. **Prohibited:** manipulating him with the data; using it as "proof" of feelings (including love); sharing it; medical claims.
**Data class:** S2, stored as compressed daily aggregates (not raw streams) unless he opts in; 90-day rolling detail, longer-term summaries only.
**Limitations:** PPG motion artifacts, fit, skin tone, ambient light, sensor lag; individual baselines vary; wearable ≠ medical device.

# SECTION V — MEMORY ARCHITECTURE

```text
                    EVA PHONE
                        │
            ┌───────────┴───────────┐
       LOCAL LLM              MEMORY ENGINE
                                   │
              ┌────────────────────┼────────────────────┐
          SQLite (SQLCipher)      FTS5              sqlite-vec
        structured memory      keyword search      semantic search
              └──────── Knowledge graph (edges table) ────────┘
```

**Stores**
1. **Core Identity Card** (~300 tokens, always loaded).
2. **Semantic memories** (facts, preferences, values) with metadata.
3. **Episodic memories** (events/conversations) stored as *summaries*, not transcripts.
4. **Project memories** (state, decisions, blockers, next steps per project).
5. **Emotional-theme memories** (S3; themes, not logs).
6. **Technical library** (Sections J–O, chunked ~150–300 tokens each) in a separate table so personal retrieval is never polluted.
7. **Graph edges** (`led_to`, `part_of`, `related_to`, `contradicts`, `supersedes`).

**Memory record** (extends the requested schema; the added fields are `kind, status, valid_from/to, triggers, supersedes`):
```json
{"memory_id":"","category":"","content":"","source":"","date_created":"","last_confirmed":"",
 "confidence":0.0,"importance":0,"sensitivity":"S0-S4","temporary":false,"expires":null,
 "kind":"said|did|pref|infer|event","status":"current|historical|uncertain|superseded",
 "valid_from":null,"valid_to":null,"triggers":[],"supersedes":null}
```
Every memory answers: **What is it? Where from? How important? Current? How confident? Sensitive? When to retrieve?** → `content, source, importance, status, confidence, sensitivity, triggers`.

**Retrieval pipeline**
```text
Query → intent + domain classifier (rule/keyword first, tiny model second)
      → domain routes: PERSONAL | PROJECT:<name> | EMOTIONAL | TECH | PREF | AUTOBIO
      → hybrid search: FTS5 BM25 ∪ vector top-k, filtered by domain
      → auth filter: drop anything above current auth state (S3+ never enters context unless step-up done)
      → score = 0.45·semantic + 0.20·keyword + 0.15·importance/5 + 0.10·recency_decay + 0.10·confidence
      → graph expansion (1 hop, capped)
      → pack into token budget (default 400–800 tokens) with status labels ("[historical]", "[uncertain]")
      → LLM
```
| Query | Route | Loads | Must **not** load |
|---|---|---|---|
| "What happened with my Delta Robot?" | PROJECT:delta_robot | Project memories + related events | Relationships, health |
| "Why do I hate losing?" | EMOTIONAL (S3 step-up) | Related pattern memories + how he's described it | Tech, project logs |
| "Explain MQTT." | TECH | MQTT chunk(s) | Any personal memory |
| "Do you remember why I started EVA?" | AUTOBIO + PROJECT:eva | Origin chain: interests → loneliness/understanding → EVA | Unrelated projects |
| "What should I do next on EVA?" | PROJECT:eva + PREF | Current state, blockers, style prefs | Emotional memories unless relevant and authorized |

**Rule:** if an S3 memory is relevant but auth is insufficient, EVA doesn't reveal it; she answers generally or asks him to unlock ("I have some relevant context, but I'll keep it private here. Want to see it on your phone?").

# SECTION W — LEARNING ARCHITECTURE

```text
Conversation → extract candidate memories → compare with existing → dedupe → detect contradiction
            → score importance & confidence → decide expiry → store / merge / ask
```

| Step | Rule |
|---|---|
| Extract | Small LLM pass (on charger) yields candidates with `kind` (said/did/pref/infer) |
| Dedupe | Cosine > ~0.90 with same category → merge, bump `last_confirmed` and evidence count |
| Contradiction | **Explicit newer statement beats older.** Old one becomes `historical` with `valid_to`, linked by `supersedes`. If ambiguous → mark `uncertain` and ask at a natural moment (not mid-crisis) |
| Importance | Base by category + repetition (3+ independent mentions = +1) + explicit "remember this" (+2) + emotional weight |
| Confidence | said/did = 0.8–0.95; preference seen repeatedly = 0.7; inference = ≤0.6 until promoted |
| Promote inference | Only after ≥3 independent observations **and** (ideally) his confirmation; even then stays tagged `infer` |
| Expiry | Temporary/task memories 1–14 days; schedule items at event end; physiology aggregates 90 days; preferences don't expire but decay in weight |
| User control | "Remember this", "forget that", "that's wrong", "what do you know about X?", weekly optional review. Deleting is real (Section T3) |
| Skill learning | Track what he asks about (not "what he knows") to infer level; never assume mastery |

**Not doing:** continuously fine-tuning a large model on his life. Personalization = **retrieval + structured memory + preference profile**. Optional later: a tiny LoRA for *style only* (never private facts), trained on-device, opt-in.

**Guardrails:** don't store emotional interpretations as facts; don't store others' private information beyond what he shared and needs; don't turn a passing remark into a permanent trait; older negative self-talk is context, not identity ("EVA should know his history without being trapped by it").

# SECTION X — MEMORY OPTIMIZATION

| Technique | How |
|---|---|
| **One strong memory > 50 excerpts** | Merge duplicates into a single record with `evidence_count` |
| Summarize episodes | Raw conversation → 2–4 sentence episode summary after 24 h; raw text dropped after 30 days unless pinned |
| Hierarchical roll-up | Day → week → month summaries per project; cold summaries archived (still searchable via FTS, embeddings dropped) |
| Tiering | **Hot** (last 30 d + importance ≥4) in RAM index; **warm** in SQLite; **cold** compressed archive |
| Embeddings | 384-d int8 ≈ 384 B/memory (float16 ≈ 768 B) |
| Ranking | Importance × recency × confidence; decay half-life ~90 d for importance ≤2, none for 5 |
| Budget | ≤ ~800 tokens of memory per LLM call; core card 300; ≤5 memories typical |
| Compression | SQLite pages + zstd for archives; store text once, reference by id |

**Rough size math:** 10,000 memories × (~60 tokens ≈ 300 B text + 384 B vector + ~150 B metadata) ≈ **~8 MB**. Technical library ~1,500 chunks ≈ **~5–10 MB**. Speech and language models (**1–3 GB**) dominate storage, not memory.
**Targets (tunable):** retrieval < 100 ms; memory-injection ≤ 800 tokens; consolidation only while charging.

CREATE TRIGGER mem_ai AFTER INSERT ON memories BEGIN
  INSERT INTO memory_fts(rowid, content, category, triggers) VALUES (new.rowid, new.content, new.category, new.triggers);
END;
CREATE TRIGGER mem_ad AFTER DELETE ON memories BEGIN
  INSERT INTO memory_fts(memory_fts, rowid, content, category, triggers) VALUES ('delete', old.rowid, old.content, old.category, old.triggers);
END;
CREATE TRIGGER mem_au AFTER UPDATE ON memories BEGIN
  INSERT INTO memory_fts(memory_fts, rowid, content, category, triggers) VALUES ('delete', old.rowid, old.content, old.category, old.triggers);
  INSERT INTO memory_fts(rowid, content, category, triggers) VALUES (new.rowid, new.content, new.category, new.triggers);
END;
